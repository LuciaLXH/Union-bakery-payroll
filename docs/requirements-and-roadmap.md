## 已确认的业务规则

| 项目 | 下一版业务依据 |
|---|---|
| 工资 | 等于基本工资加社保补贴。以实际录入金额为依据，不能重复加补贴。 |
| 社保 | 老板明确本版可以不用管；不再沿用旧版统一扣 1000 元的计算。 |
| 普通缺勤 | 每天分别扣工资、月绩效、月全勤的 1/30。 |
| 旷工 | 当天不发，另外扣两天工资；总共三天，不是四天。 |
| 迟到 | 每迟到 1 分钟扣 1 元。 |
| 加班 | 工资折算时薪后乘 1.5，每日 9 小时，每月取 30 天。 |
| 工资与营业额 | 绝大部分员工工资不挂钩营业额。普通核算不应依赖营业额或沿用统一人效门槛。少数例外尚无具体规则。 |
| 学徒工作失误 | 可以在工资条指出，但不因失误自动扣款；不沿用次数、200 元阈值和自动公摊规则。 |
| 职级 | 需要区分零基础学徒、有基础学徒；更多等级及标准以后补充。 |
| 合计 | 工资表中的合计就是最终实发金额。 |
| 门店上限 | 手动填写上限，与该店当月所有员工最终实发金额之和比较；不另加单位社保等成本。 |
| 晋升限制 | 达到或超过上限时，职级也不能提升。低于上限只是有预算空间，不代表自动晋升。 |

## 核算公式与算例

### 输入定义

- W：月工资，已经包含社保补贴。
- P：扣缺勤前的月绩效金额；A：扣缺勤前的月全勤金额。
- n：普通缺勤天数；m：旷工天数。同一天不能同时计入 n 和 m。
- t：迟到分钟数；h：已确认的有效加班小时数。
- C：本月通勤补贴。第一版建议由老板填写本月实际应发补贴，不自行按缺勤折算。

原表只有旷工天数。老板后续分别回复了普通缺勤与旷工的处理方式，因此建议新增普通缺勤天数字段，并清楚提示不要重复录入。此处区分只用于承载两种计算方式，不要求老板重新解释术语。

### 公式整理

```text
工资扣款 = W / 30 × (n + 3m)
绩效扣款 = P / 30 × (n + m)
全勤扣款 = A / 30 × (n + m)
迟到扣款 = t × 1
加班费 = W / 30 / 9 × 1.5 × h

合计 = W + P + A + C + 加班费
       - 工资扣款 - 绩效扣款 - 全勤扣款 - 迟到扣款
```

旷工公式按照“额外两天工资”只作用于工资项整理，绩效和全勤扣当天份额。这是本轮对回复的公式化表达，后续用老板测试表对账验证，不把下列推导金额冒称为老板给出的算例。普通缺勤和旷工的扣款均采用未扣减前的月度金额；加班基数也采用 W，不使用扣完考勤后的余额。

这套公式不自动引入试用期八折、职位固定工资、额外报损或客诉扣款、迟到导致整月全勤取消等旧版或未经确认的规则。若以后需要其他加减项，应单独记录金额、原因及确认状态。

### 虚构验收算例

统一采用 W = 4500、P = 600、A = 300，未说明的通勤补贴、天数、分钟和小时均为 0；每行独立计算。

| 情况 | 工资扣款 | 绩效扣款 | 全勤扣款 | 迟到扣款 | 加班费 | 合计 |
|---|---:|---:|---:|---:|---:|---:|
| 无缺勤与其他变化 | 0 | 0 | 0 | 0 | 0 | 5400 |
| 普通缺勤 1 天 | 150 | 20 | 10 | 0 | 0 | 5220 |
| 旷工 1 天 | 450 | 20 | 10 | 0 | 0 | 4920 |
| 迟到 7 分钟 | 0 | 0 | 0 | 7 | 0 | 5393 |
| 有效加班 2 小时 | 0 | 0 | 0 | 0 | 50 | 5450 |
| 本月通勤补贴 200 元 | 0 | 0 | 0 | 0 | 0 | 5600 |
| 学徒新增失误备注 | 0 | 0 | 0 | 0 | 0 | 5400 |
| 普通缺勤 1 天且旷工 1 天 | 600 | 40 | 20 | 0 | 0 | 4740 |

门店上限设为 30000 元时：总实发 29999.99 元显示有预算空间；30000 元及以上显示暂不能晋升。未填写上限时显示未设置，不能把空值当作 0 元或无限预算。未录齐员工或存在待核算记录时，门店总额只作为暂算结果。

金额处理建议：使用十进制金额，各项最终金额按四舍五入保留两位，再以这些金额计算合计；日薪和时薪保留精度到项目金额计算完成。舍入顺序属于实现建议，后续用测试表检查分位差异。若算出负数，提示异常、保留计算明细并要求核对，不沿用旧代码静默归零的做法。

## 数据保存与权限方案

### 用户目标

老板持续维护数据，不再每个月都上传文件。真实数据可以只授予老板访问权，开发者使用结构相同、内容虚构的测试环境。用户希望先自行测试云端方案，暂不就云端保存再次询问老板。

### 建议的记录结构

| 记录 | 内容与目的 |
|---|---|
| 门店与月度上限 | 门店编号、名称、月份、上限。每月保存一份，避免以后改上限影响历史。 |
| 员工与职级 | 稳定员工编号、姓名、入职日期、当前门店、岗位、职级及常用工资设置。 |
| 月度核算输入 | 员工、月份、当月门店及职级、W/P/A/C、普通缺勤、旷工、迟到、加班和失误备注。 |
| 核算批次与结果 | 使用的输入版本、规则版本、各项扣款、实发金额、确认时间和工资条所需资料。 |
| 变更记录 | 修改对象、修改前后值、时间、操作者；正式使用时支持追溯。 |

一般场景下，同一员工同一月份只保留一个当前核算记录；更正通过版本保留历史。跨店分摊或同月多段工资先留作后续扩展，不在第一版猜测分配方法。

建议保留 Streamlit，增加独立的数据访问层，让计算函数只接收明确输入并返回结果，避免界面、数据库和公式混写。先在本地持久化测试库中验证保存流程，再接云端测试库。若后续采用不同数据库引擎，需要另做数据库兼容验证，不能把本地通过当作云端已验证。

日常操作建议使用像表格一样的管理页，老板修改后保存到数据库；数据库平台的管理控制台可用于管理维护，但不必成为老板日常录入工资的入口。Excel 保留作初次导入、对账和导出工具。

### 正式环境边界

正式云账号、数据库和部署权限由老板持有，程序只获得所需权限；开发者不持有正式数据、连接密钥、备份或含工资内容的日志。仅不发数据库账号不足以隔离数据：若开发者仍可控制正式程序部署、密钥或服务器，也可能间接访问数据。正式版本应由老板或其指定维护者控制发布，开发环境不自动连接正式库。

云服务厂商、地区、套餐、登录方式及正式发布流程尚未选定。本阶段不创建付费资源，也不把虚构测试成功描述成正式数据权限已隔离。

## 页面和核算状态建议

建议按工作顺序组织四个入口：

1. 员工资料：维护门店、员工、入职日期、岗位、职级及常用工资。
2. 本月核算：选择月份与门店，带入员工资料，填写变动项，保存、计算和查看明细。
3. 门店汇总：汇总完整的当月实发，填写上限，显示余额、使用情况及晋升限制。
4. 工资条与历史：预览个人工资条，确认批次，导出和查看历史版本。

状态至少区分草稿、待重新核算、已核算、已确认。任何金额或考勤输入变更后，旧结果应标为过期；过期结果不能被当作最终工资导出。核算时固定同一份输入，预算页和工资条使用同一版本结果。

员工以后调薪、改名、换店或调整职级，不应改变已确认的历史工资条。更正已确认月份时保留旧版和原因。预算只是晋升限制，不自动减薪，也不自动执行晋升。

个人工资条保留老板熟悉的项目，增加扣款明细以便核对。门店预算和其他员工数据不出现在个人工资条。先提供总表与个人工资条 Excel，PDF 或图片格式根据原型反馈再定。历史模板参考仅用于字段和排版，不直接复用其计算规则。

## 实施顺序与完成标准

### 第一阶段 新公式和数据字段

状态：已实现，测试与具体运行方法见 README。

统一字段及单位，建立上述虚构算例；重构计算模块，去掉不适用的默认规则，保留各项计算明细。无需真实数据即可开始。

完成标准：所有独立及组合算例通过；改变社保标记、学徒失误备注或营业额，不会意外改变普通工资结果；输入缺失、非法金额及天数能得到明确提示。

### 第二阶段 数据保存和录入流程

建立独立数据访问层、本地测试库及员工/月度记录；页面支持直接维护数据、带入常用值和明确保存。同步处理输入修改后结果失效，避免继续依赖每月上传文件。

完成标准：重新打开应用后仍能恢复已保存草稿；同名员工不会混淆；修改员工当前工资不改变已确认历史；重算保留已保存调整。

### 第三阶段 汇总和工资条

实现门店上限输入、完整批次汇总、达到上限的限制提示；完善个人明细、确认流程及 Excel 导出。增加与旧表合计的差额对账。

完成标准：网页合计、个人工资条、门店汇总和导出一致；上限恰好相等时受限；修改输入后旧结果不能直接作为最终版导出；不同会话不会互相覆盖文件。

### 第四阶段 云端测试和老板验收

用户先用虚构数据选择并验证云端数据库与部署方案，测试登录、访问限制、断线错误及备份恢复；然后让老板在自己掌握的环境中录入测试样例或做一月对账。正式数据和权限移交在测试通过后完成。

完成标准：无权限身份无法读取工资；开发环境与正式数据隔离；正式访问权和发布权归属清楚；老板原表与系统差异均能解释。测试通过前保留原有算薪方式。

## 留待样例或原型验证的边界

这些事项不阻塞第一阶段，不需要现在再发一份长问卷：

- 通勤补贴是否自动与考勤联动：第一版建议填当月实际金额，不推导。
- 月中入离职、半天缺勤、跨店工作、试用期及少数营业额关联员工：有相应样例后扩展，不直接使用旧版假设。
- 迟到是否额外影响全勤：目前只确认每分钟扣 1 元，不擅自增加联动扣款。
- 非学徒失误、其他福利或投诉是否涉及金额：现阶段不自动生成这类扣款；备注与金额分开。
- 晋升后金额预演、职级标准、职级变动生效月：当前只实现已确认的预算限制与手动管理建议，不自动决定或追溯修改工资。
- 实际 Excel 是否含合并单元格、多张表或额外标题，以及老板的金额舍入习惯：收到样例后验证兼容性。

接下来用虚构员工完成网页整月验收，再推进个人工资条与确认锁定。无需等待老板分享真实名单或真实营业额。
