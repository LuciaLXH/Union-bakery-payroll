# 后续功能路线图 / Product roadmap

状态：规划中；下列功能尚未上线。2026-10-25 用户已反馈本轮问题解决，后续讨论正式上线；本清单不自动启动开发。阶段记录见 [AI 录入改造与交接](2026-10-25-ai-entry-handover.md)。

## 1. 个人工资条：先预览和下载，再考虑邮件

**老板看到的效果：** 选门店和月份，查看每人的工资组成、逐项扣款、加班费、实发和备注；确认后下载单份 PDF 或整店压缩包。

**需要做的工作：** 以某一次确定的核算版本生成工资条，保存规则版本、输入版本、生成时间和工资条版本。修改考勤后，旧工资条标记为已被新版本替代；不能将旧金额当作当前金额再次发出。

**拟增加的数据：** `payslips`（核算记录 ID、版本、生成状态、文件位置、内容校验值、生成时间）。不把永久公开的文件地址写进页面；真实数据阶段使用受保护存储和短期下载链接。

**验收：** 工资条金额与核算明细一致；中文姓名、长备注和分页清楚；一人一份不混入其他员工内容；重复生成可追踪，旧版本不冒充新版本。

## 2. 身份、门店权限与出勤提交

**店长看到的效果：** 先提供适合手机的专属网页链接，登录后只看到自己门店和当月员工，填写考勤、保存草稿、提交给老板。先验证网页流程，再决定是否需要微信小程序。

**老板看到的效果：** 每家门店显示“未开始 / 草稿 / 已提交 / 待修改 / 已确认”，可以查看、退回并给出修改意见。店长默认只填写考勤和备注，是否显示工资金额由老板决定。

**需要做的工作：** 独立账号、门店成员关系、服务端权限校验、提交与退回流程、修改记录。不能只靠隐藏按钮或在网址里写门店编号来隔离数据。确认后的出勤或发薪记录修改需要重新打开并保留原因。

**拟增加的数据：** `users` 或外部身份 ID、`store_memberships`、`attendance_submissions`、`audit_events`；必要时将纯考勤输入与工资快照权限拆分。

**验收：** A 店店长不能通过改链接访问 B 店数据，也不能访问受限工资接口；移动端可完成录入；重复提交不重复建记录；老板确认前可以退回修改。

## 3. 邮件发送：在确认和权限流程之后接入

**老板看到的效果：** 先预览收件名单、工资条版本和邮件内容，确认发薪记录后再发送。页面显示待发送、发送中、服务商已接受、失败和退信；可以对失败项重试。

**需要做的工作：** 验证员工邮箱与员工编号的对应关系，设置门店发件地址；接入邮件服务商和后台任务；敏感文件使用受保护访问。前期先用测试邮箱和虚构 PDF 验证流程。是否在批准后自动发送，作为单独设置。

**拟增加的数据：** 员工联系信息与验证状态、`email_outbox`、`delivery_attempts`、幂等键（员工＋月份＋工资条版本＋渠道）、服务商回执 ID。发送重试必须复用幂等标识，避免重复投递。

**验收：** 未确认月份不能发送；一人对应一份已确认工资条；重复点击不重复发送；错误邮箱被拦截或可追踪；失败重试不会更换附件；“服务商已接受”不等同于员工已经收到或阅读。

## 4. 老板的数据分析 Dashboard

**先交付的效果：** 按门店、月份筛选，查看月度实发、工资组成、加班费、迟到与缺勤、人数变化以及环比趋势。每张图可追溯到对应月份和当前有效核算版本。

**口径要求：** 同一员工同一月份只取当前有效版本；旧核算记录不重复相加。草稿、待核算和已确认月份分别标识。没有历史月份时显示“暂无历史”，不能伪装成 0 或编造增长率。

**拟增加的数据：** 首版复用现有工资业务表建立查询或视图。等实际数据量需要时才增加汇总表。若希望看人工成本率，需要另行提供口径一致的门店月营业额与其他用工成本；目前工资数据本身无法算出可信的成本率。

**验收：** 图表合计与月度工资页相等；改动并重算后自动取新版本；未核算员工有清楚提示；无上期数据不计算环比；门店权限同样适用于导出和分析接口。

## 5. 发薪前与上月工资表对比

**记录日期：2026 年 10 月 25 日。状态：已记录需求，暂不开发。**

**用户提出的场景：** 本月工资核算好、准备发放前，将同一家门店本月与上月的工资表放在一起对比，让老板直观看到变化，作为最后一次核对。与长期的月度工资分析并列，重点是当次发薪前检查。

**后续设计建议（具体展示方式待开发前确认）：**

- 门店汇总：并排显示上月、本月实发总额及增减金额。
- 员工明细：按稳定员工编号对应，展示每人的上月实发、本月实发及差额，突出有变化的员工。
- 变化依据：可展开查看约定工资、缺勤扣款、迟到扣款、加班费、补贴等项目的差异。例如“本月比上月少 180 元”，继续查看具体哪些项目发生变化；仅根据记录展示，不猜测原因。
- 名单变化：单独标出仅出现在本月或上月的员工；是否属于入职、离职或调店，应依据档案及历史记录核对。

**数据口径：** 对比同店相邻两个自然月的有效核算版本，并标明版本和确认状态。有正式发薪确认流程后，上月应对照实际确认发放的版本；目前“已计算”不能当作“已发薪”。没有上月数据时明确提示，不能用 0 代替。输入修改导致结果失效时，应先重新计算。此功能只辅助核对，不自动确认发薪、修改金额或转账。

**拟验收：** 两个月合计分别与对应工资表一致；员工差额汇总与门店总差额一致；无历史、名单变化和版本更正均有清楚提示。

## 6. Excel 员工与门店档案识别导入

**状态：未实现，暂缓；2026-10-25 用户决定先询问老板意见，后续再决定是否开发。**

设想流程为：上传老板现用 Excel → 识别员工、门店和约定工资字段 → 人工核对预览与重复项 → 确认后批量建立或更新档案。若决定实施，再依据脱敏样表确定实际列名、格式和更新规则，不默认覆盖现有档案。

当前已上线的 AI 仅整理考勤及备注并写入已有员工的月度记录；网页员工表格可以批量编辑，但旧 Excel 导入只做临时试算，不会建立永久档案。

## 建议顺序

### 2026-11-02 最新决定：实施 AI 录入流程简化，先测试再上线

面向老板使用业务语言，避免“写入”等技术用词。拟改为“输入记录 → 整理记录 → 核对每条事项及工资影响 → 确认以上记录并计算工资”，由一个主按钮完成保存和计算；可保留“先保存，稍后计算”。涉及多店时明确显示计算范围，报损尚不扣款时明确说明。保留修改与取消能力。

2026-10-28 用户要求先记录；2026-11-02 已明确授权开始执行。现已实现上述流程，并完成142项本地测试与浏览器回归。发布顺序为中文测试站实际验收后再更新老板正式站；部署结果以[本次发布记录](2026-11-02-ai-flow-release.md)为准。价格导入与报损扣款不在本次发布范围。完整背景见[本轮核算检查](2026-10-28-calculation-review.md)。

### 2026-10-28 新增优先事项：价格资料与报损扣款

**2026-11-02资料更新：** 已收到供应商明细截图及文字报价，整理为11项原料的价格参考，具体采购资料仅保留在本地私有工作记录中。需核对芝士片计价单位、面粉简称、零价记录及价格适用范围。仅完成资料整理，未导入数据库或启用扣款；成品面包零售价和自制馅料/面头成本仍缺。

老板提出用现有 Excel 表格提供原料成本和产品售价，供报损核算查询。当前没有价格资料表、价格导入或报损扣款计算；这与员工建档导入是不同功能。排查记录见 [本轮核算检查](2026-10-28-calculation-review.md)。

拟定流程：上传 Excel → 对照列名、单位和重复品项预览 → 确认入库 → AI 提取员工、报损品项、日期和数量 → 查询有效价格 → 展示计算明细 → 核对后写入月度工资并重新计算。

- 资料需区分成品、原料、馅料、面头，记录编号、名称/别名、规格、计价单位、售价或成本单价、适用门店及生效日期；具体列映射以老板实际样表为准。
- 已确认规则为成品面包售价的一半、馅料/面头成本价。新增提到的面粉可作为原料成本资料；是否用于员工扣款以及适用范围仍需结合老板例子确认，不能把所有库存损耗自动算成员工责任。
- 包装价需有明确规格才能换算，例如25公斤/袋、每袋100元可得到4元/公斤；不能推测袋重、配方或损耗率。若需要从配方推导馅料/面头成本，则需另有配方与产出量，首版可直接维护经老板核定的单位成本。
- 员工报损明细保存事件日期、品项、数量/单位、价格版本、采用单价、扣款比例、计算金额、原文和核对状态，并关联当月工资；历史核算保留价格快照，后续调价不改写已确认工资。
- 匹配不唯一、价格缺失、单位不可换算时提示补充，不猜价；重复导入/重复事件须防重。需要把明细与扣款合计接入计算、历史、Excel导出、确认锁定和更正流程。

**下一步输入：** 老板现用原料成本/产品售价 Excel 样表，以及一条“报损记录 → 应扣金额”的真实业务例子（可脱敏）。本轮只排查与记录设计，未创建正式库新表或发布新功能。

1. 本轮已反馈的问题修复并获得用户测试确认；老板单人正式版已补专用登录、确认锁定、发放标记、更正审计与备份恢复工具，见[操作与维护说明](production-owner-guide.md)。正式使用前仍需首月业务对账；多角色权限未实现。
2. 交付个人工资条预览与下载，可独立验收。
3. 建立账号、门店权限与确认流程，然后交付店长手机填报链接。
4. 接入经过确认的邮件发送与失败重试。
5. 用已稳定的月份数据搭建 Dashboard；基础趋势可与第 3 阶段并行。

新增的“发薪前与上月工资表对比”先保留在需求清单中，后续可作为独立小功能安排，不要求等完整 Dashboard 做好；当前不改变开发优先级。

现在不需要再发一长串问题给老板。进入各阶段前只确认对应事项：工资条必要字段与版式；店长是否能看金额、谁确认；员工邮箱由谁维护与发件人；Dashboard 最重要的三个指标。

## English summary

| Phase | User outcome | Dependency |
|---|---|---|
| Payslip preview and PDF download | Explain one employee’s pay from a specific calculation version | Stable calculations and version references |
| Identity and scoped manager attendance | Managers submit only their own store’s attendance | Server-side roles, store membership and review workflow |
| Reviewed email delivery | Send the approved payslip to the verified recipient with delivery tracking | Approved payroll, verified contact data, outbox and idempotency |
| Monthly analytics | Compare current payroll totals, overtime, absence and headcount | Defined metrics, version-aware queries and enough history |

These are planned capabilities. The public English demo sends no emails and has no manager accounts or analytics dashboard. Payroll cost ratios require revenue and additional cost data that the current system does not collect.
